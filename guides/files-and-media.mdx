# Files and media

ECP (Execution Control Protocol) moves binaries as **file references**, not as inlined bytes in the workflow graph.

## FileRef

A `FileRef` is a tagged object with `kind`:

- `{ kind: "file", path }` — a host path on Node, or an `ecp://browser/<id>` locator in the browser
- `{ kind: "artifact", uri }` — bytes the host already stored (`ecp://file/…` on disk)
- `{ kind: "url", url }` — a remote URL (opt-in with `allowRemoteUrls`)
- `{ kind: "buffer", data }` — base64 bytes (tests and small fixtures)

Do not embed secret paths or credentials in the ref. Use `secrets("key")` for credentials; pass the ref as data.

## Resolve and write

Plugin code uses host helpers:

- `resolveFile(ref, ctx)` — read bytes (and metadata) for a `FileRef`
- `writeMediaArtifact(bytes, { mediaType, name, prefix }, ctx)` — persist output and return a new `FileRef`

These live on the execution context. Plugins never import Node or browser hosts. The bound environment supplies a `MediaStore`:

- **Node** writes under `.ecp/artifacts` (override with `ECP_ARTIFACTS_DIR`) and returns `ecp://file/…` refs. `{ kind: "file", path: "./photo.jpg" }` reads that path from disk.
- **Browser** keeps bytes as `ecp://browser/<id>` refs. When you pair a Node host (`ecp app`), the browser store uploads those bytes to `POST /v1/media` so the host saves them on disk.

Remote blob upload and download stay an explicit plugin step (`@executioncontrolprotocol/plugin-azure-blob-storage`), not a store tier.

## Journals

Run artifacts and events live under `.ecp/runs/<runId>/` (override with `ECP_RUNS_DIR`). The journal records step outputs, including file refs. See [Journal](/reference/journal).
