---
title: "Connect over MCP"
description: "Give Claude, Cursor, or any MCP client the three ECP (Execution Control Protocol) tools, retrieve, execute, and commit, with the ecp mcp start stdio server."
---

`ecp mcp start` runs an MCP server over stdio that gives any MCP client the full ECP (Execution Control Protocol) loop through three tools. It forwards every call to the local [host](/guides/host), so an agent in Claude, Cursor, or another client sees the same capabilities, saved executions, and runs as the CLI.

## The three tools

| Tool | Does |
| ---- | ---- |
| `retrieve` | Read capabilities (with their `accepts` and `returns`), executions, configs, runs, plugins, formatters, and editor schemas |
| `execute` | Validate or run an execution given inline, by `path`, by `id`, or as `{ id, patch }`; resume or cancel a run |
| `commit` | Create, update, or delete stored executions and configs |

Their input schemas are the [operation](/reference/operations) inputs, so a tool call takes the same JSON as the HTTP API. The tool list is fixed: installing plugins adds capabilities behind `retrieve`, not new tools, so the list stays small no matter how many capabilities you have.

There are no per-capability tools, no resources, and no prompts.

## Claude Code

```bash
claude mcp add ecp -- ecp mcp start
```

## Claude Desktop

Add the server to `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "ecp": {
      "command": "ecp",
      "args": ["mcp", "start"]
    }
  }
}
```

## Cursor

Add it to `.cursor/mcp.json` in your project (or the global file):

```json
{
  "mcpServers": {
    "ecp": {
      "command": "ecp",
      "args": ["mcp", "start"]
    }
  }
}
```

## Other clients

Any client that can launch a stdio server works: the command is `ecp`, the arguments are `mcp start`. To keep a separate store for a project, set `ECP_HOME` in the server's environment.

## How a session goes

1. The agent calls `retrieve` with `{ "type": "capability", "query": "csv" }`, then with an `id` to read a capability's schemas.
2. It writes an execution and calls `execute` with `{ "execution": { "path": "flow.ecp.json" }, "mode": "validate" }`.
3. It fixes the issues it gets back and validates again until the result is valid.
4. It runs: `{ "execution": { "path": "flow.ecp.json" }, "input": { ... } }`.
5. It saves the working execution with `commit`, and runs it by `{ "id": "..." }` next time.

Each tool result has a text rendering and `structuredContent` with the same data. Failed operations come back with `isError: true` and one line per issue:

```text
ECP_MANIFEST_INVALID — 1 validation error
/steps/1/uses: ECP_CAPABILITY_UNKNOWN — Capability @executioncontrolprotocol/test.ech is not installed. (did you mean '@executioncontrolprotocol/test.echo'?)
```

## Paths and large results

- Relative paths, in `execution.path`, `output.path`, and file references in inputs, resolve against the directory the client started `ecp mcp start` in. Prefer paths over inline manifests for local files.
- Pass `output: { "path": "result.json" }` to write a large result to a file and get a short summary back instead of filling the context window.

## Host restarts

The relay finds the host through `$ECP_HOME/host.json` on every call and starts one if needed. During a restart (for example after a plugin install), it waits and retries. If a run's connection drops mid-call, the relay finds the run when the host is back; an `interrupted` run tells the agent to call `execute` with `resume`.

## Secrets stay out

Secret values never pass through MCP. `retrieve` returns config objects with `$secret` references only, and there is no tool to set a secret. When a run fails with `ECP_SECRET_MISSING`, the agent should ask you to run `ecp config secrets set <key>`.

## Debugging

The relay writes nothing to stdout except MCP messages. Its log is `$ECP_HOME/logs/relay.log`; the host's is `host.log` in the same folder (`ecp host logs`).
