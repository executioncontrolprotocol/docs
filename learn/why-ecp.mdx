# Why ECP

Agents already call tools. What they rarely do well is **delegate a plan** that another process can validate, govern, replay, and repair.

ECP (Execution Control Protocol) is that delegation layer. You keep reasoning in the model. You put the repeatable part in a workflow file and run it through a host that plugins and policies can audit.

## The problem

A one-off tool call is cheap. A sequence of calls with secrets, cost limits, and media is not. Without a protocol you get:

- Hidden bindings mixed into the graph
- Failures that only exist as chat text
- No way to resume or rerun from a named step
- No shared language for “this plugin is missing” vs “this input is invalid”

## What ECP adds

| Need | Mechanism |
| ---- | --------- |
| Portable graph | Workflow manifest (`@executioncontrolprotocol.workflow`) |
| Host bindings | Requirements document (`@executioncontrolprotocol.requirements`) |
| Structured failure | `ECP_*` codes and `--json` envelopes |
| Replay | Run journals under `.ecp/runs/<runId>/` |
| Governance | Policies (budget, approval, state-control, registry-control) |
| Extensibility | npm plugins that generate CLI commands |

## What ECP is not

- Not a full agent harness. The CLI is a capability the harness operates.
- Not MCP. MCP is how models talk to tools; ECP is how an agent **delegates** a governed graph. See [Relationship to MCP](/learn/relationship-to-mcp).
- Not a prompt. The workflow file is source of truth; the model authors and repairs it.
