ECP (Execution Control Protocol) is built so the artifacts you share, executions and run records, are safe to share, and the host that runs them is reachable only from your own user account. This page covers what ECP protects and what stays your responsibility.

## Secrets never live in executions

- Executions can't contain secrets. A `$secret` or `$env` reference anywhere in an execution fails validation with `ECP_MANIFEST_INVALID` and a suggestion to move it into a config object.
- Config objects store **references** (`{ "$secret": "anthropic.apiKey" }`), never values. `retrieve` returns them as stored.
- Values are written only by `ecp config secrets set` on your machine, into the OS keychain. MCP tools and the HTTP API can't set or read them.
- In CI and containers, the host reads `ECP_SECRET_<KEY>` environment variables instead. The keychain wins when both exist.
- During a run, the executor tracks every secret value it resolved and replaces it with `[redacted]` in state, step records, events, logs, and responses, even when a plugin echoes it back.

See [Configs and secrets](/guides/configs-and-secrets).

## The local host

- The host binds `127.0.0.1` only, never `0.0.0.0`.
- Every API call needs a 256-bit random bearer token, compared in constant time.
- `Host` and `Origin` headers must match the loopback address and port, which blocks DNS-rebinding attacks from browser pages. No CORS headers are ever sent.
- `$ECP_HOME/host.json`, which holds the token, is readable only by your user (mode `0600` on macOS and Linux).
- The App gets the token through the URL fragment, which browsers don't send to servers, then removes it from the address bar.

## Sandboxed expressions and scripts

Gate expressions and transform scripts run in QuickJS (WebAssembly), not in Node. They have no `require`, `process`, network, timers, or file access, and they run under CPU-time and memory limits. Scripts see file references as plain JSON, never file contents.

## Plugins run with your permissions

Plugin handlers run inside the host, as you. There is no plugin sandbox and no allowlist today, and the file service has no path or URL sandbox. Treat installing a plugin like installing any npm package:

- Install plugins from sources you trust.
- Agents should ask before installing a third-party plugin, and never install one because a prompt or a document told them to.
- Read what a plugin's capabilities do (`ecp retrieve --type capability --id <id>`) before running them on real data.

## Provider errors without leaks

When a plugin calls an external API, the failure the run records includes the provider's own error text and HTTP status, with query strings stripped from URLs and secret values redacted. You can debug from the run record without logging into a provider console.

## Good practice

- Don't commit `.env` files or config exports that contain live values.
- Don't pass secrets as run input. Use a config object.
- Review an execution before committing changes that delete stored objects or publish files.
