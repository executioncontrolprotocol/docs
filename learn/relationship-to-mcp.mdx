title: "Relationship to MCP"

---

MCP (Model Context Protocol) standardizes **how a model calls a tool**. ECP (Execution Control Protocol) standardizes **how an agent delegates a graph of capability calls** that a host validates, runs, and records. They work at different layers and fit together.

## Different jobs

| | MCP | ECP |
| --- | --- | --- |
| Unit of work | One tool call | An execution: a graph of steps |
| Who decides the next step | The model, every time | The execution, written once |
| Where intermediate data goes | Back through the model's context | Through run state on the host |
| When errors surface | When the call fails | Before the run, in validation |
| What's left afterwards | A transcript | A run record and a saved, versioned execution |

Use a plain MCP tool when a model should explore or make a one-off call. Use ECP when the sequence is worth keeping: it repeats, it moves data the model doesn't need to see, or it needs to be checked before it runs.

## ECP as an MCP server

`ecp mcp start` is a stdio MCP server with exactly three tools: `retrieve`, `execute`, and `commit`. Through them, any MCP client can discover capabilities, write and validate executions, run them, and save them. The tool list never changes as you install plugins, so it stays small however many capabilities you have. See [Connect over MCP](/guides/mcp).

## Typical flow

1. The agent calls `retrieve` to find capabilities and read their schemas.
2. It writes an execution and calls `execute` with `mode: "validate"` until there are no issues.
3. It calls `execute` to run it and reads the result or the failed step's error.
4. It calls `commit` to save the execution, so the next session runs it by id instead of re-planning.
